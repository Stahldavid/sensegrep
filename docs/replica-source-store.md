# Deduplicated source replicas

A replica destination is a private directory owned by the current user. Its first import binds it immutably to one explicit repository UUID. Different repository identities require different destinations. Sharing a destination within that authorized repository permits physical reuse without allowing an import from another repository to reuse its storage scope implicitly.

Objects are raw bytes stored once by SHA-256 under `.replica-objects/sha256`. Snapshot artifacts remain `<snapshot-hash>.json`, but their `storage: source-replica-v1` marker identifies a small immutable manifest, not an embedded base64 bundle. The manifest retains paths, hashes, repository identity and snapshot identity. Reading reconstructs and validates a wire-compatible version-1 source bundle. Original BOM and newline bytes are preserved. This does not import or activate a vector index.

`getReplicaObject` returns verified local bytes or `undefined` when absent; corrupted bytes are errors. Callers should pass the expected repository UUID, or establish the binding with `verifyReplicaRepository` first. `putReplicaObject` verifies identity before atomic publication and leaves valid unreferenced objects available for retry after an interrupted transfer. This supports fetching only missing objects. Interrupted imports can leave bounded orphan cache entries, but no snapshot is advertised until its complete manifest is published.

The destination guard serializes import, collection, pinning and complete snapshot reads across cooperating local processes. A crashed guard fails closed and must be recovered manually only after all users have stopped. Atomic publication uses a temporary file, file synchronization and an exclusive hardlink; durability of the containing directory across power loss is not asserted.

By default, imports retain the eight most recently stored unpinned snapshots and every explicitly pinned snapshot. Reimporting a snapshot refreshes its retention time. Set `SENSEGREP_REPLICA_RETAIN_SNAPSHOTS` or supply `retainSnapshots` to change the ordinary snapshot count. `pinReplicaSnapshot` retains a snapshot until `unpinReplicaSnapshot`; `removeReplicaSnapshot` refuses a pinned snapshot. A pin is an explicit retention promise and may outlive its original process. Readers hold the guard while reconstructing all objects, preventing eviction during a read.

`SENSEGREP_REPLICA_MAX_BYTES` (default 512 MiB), or `maxBytes`, limits completed unique source-object bytes. The collector first expires excess unpinned manifests, then evicts unreferenced object-cache entries oldest first when space is required. If retained or pinned objects prevent admission, import reports capacity instead of silently deleting those references. Manifest and filesystem metadata, temporary publication space, and deliberately pinned metadata are outside the source-byte budget. Each file is limited to 2 MiB, each wire bundle to 32 MiB, and each manifest to 10,000 files and 4 MiB encoded size. Pins and final objects are never inferred from a branch or path.

The regression tests use separate processes for concurrent imports and collection, validate physical object counts across different snapshots, verify wrong-repository and corrupt-object rejection, exercise partial-import cache reuse, and prove that pinned snapshots survive ordinary retention. They do not establish a distributed filesystem protocol; each executor maintains its own local replica directory.
