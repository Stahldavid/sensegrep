# Shared provider quota on one host

Set both `SENSEGREP_SHARED_QUOTA_DIR` (a trusted local directory writable by participating processes) and `SENSEGREP_SHARED_QUOTA_SCOPE` (an opaque, non-secret identifier for a common provider quota) to coordinate embedding request and token limits across processes on the same machine. Use the same directory, scope, RPM and TPM in every participating process. All requests under the scope consume the same budget, even if credentials differ; use different scopes for independent quotas. The scope is hashed for the directory name. Do not put credentials in the scope.

Configure finite RPM/TPM using the existing embedding rate-limit settings; infinite limits do not impose a quota. The shared limiter reserves the estimated request and input tokens before a provider call. Cancellation while waiting does not reserve capacity. A request that is cancelled or fails after reservation remains charged for the window. A crashed guard owner blocks new reservations rather than risking an overrun. After verifying all clients are stopped, inspect and remove only the abandoned `guard` directory. A malformed state or mismatched limits fails closed. To change limits, stop all clients, wait at least a full prior quota window, then remove `window.json` for the scope; preserve its guard and other active scopes.

This is local-filesystem coordination and assumes all participants share a filesystem with working atomic directory creation and rename, the same system clock, and a trusted directory. It is not a distributed or cross-machine coordinator; do not use a shared mutable network filesystem to imply one. Token counts are estimates, not provider-reported usage. A process can pause between reservation and the actual request, so the recorded window may differ from the provider window. Wall-clock jumps forward can expire reservations early. State publication uses atomic rename but does not fsync, so OS crashes or storage durability failures can lose a reservation. These limitations prevent a strict provider-quota guarantee. The limiter does not infer external provider usage or enforce quota for applications that do not participate. Cross-process fairness is not guaranteed. The shared state contains request times and token estimates, not source text or credentials.
