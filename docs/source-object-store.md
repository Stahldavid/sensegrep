# Historical indexed source objects

New full, incremental and watched indexing writes the original bytes used by the parser into a per-index content-addressed store before publishing metadata for those bytes. The object key is the lowercase SHA-256 of the raw bytes, including BOM and CRLF. The store lives at `.source-objects/sha256/<digest>` beneath the resolved index storage directory, so checkout and profile isolation follow the index binding. With `SENSEGREP_SHARED_OBJECTS=1`, explicitly registered checkouts in the same repository scope publish a shared physical object under the repository directory and hard-link it into each local CAS. Raw content is independent of profile and is shared across those profiles; metadata and source locations remain private to each view. Different repository UUIDs and unregistered checkouts do not share objects. Across filesystems the local link can fall back to a separately verified local copy; across executors local bytes are replicated rather than sharing a mutable directory.

Publication writes and syncs a uniquely named temporary file, then creates the final name exclusively with a hard link. Concurrent writers for identical content verify and reuse the existing object. A corrupt or symbolic-link object is rejected and never silently replaced. Reads enforce a byte limit and verify the digest before returning content. `ENOENT` means historical content is absent; corruption, unsafe files and oversized content are different failures and must not trigger a silent live-source fallback.

Objects survive inactive-generation collection so a source reference can remain usable after the live file changes. Shared repository objects use the guarded retention policy and byte budget in `shared-source-retention.ts`; local CAS links pin the shared object. Objects without local links can be evicted by age/size. A new object that cannot fit alongside pinned objects is rejected instead of exceeding the configured shared budget. Local CAS retention remains tied to the index/view lifecycle and must be pruned through the view retention contract. Explicit removal of an entire index also removes its object store. Old metadata and unchanged files from before this implementation may lack objects; a caller may use a separately hash-validated live read only when historical content is absent. A full rebuild captures those objects.

This provides atomic publication for cooperating processes on the local filesystem and verifies subsequent reads. It is not a sandbox against another process with write access, a durability guarantee across filesystem or power failure, or a complete repository snapshot. Source objects contain private source bytes and should remain within the index's protected storage.
