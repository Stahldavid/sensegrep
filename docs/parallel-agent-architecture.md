# Architecture for parallel agents

The unit of mutable local ownership is a checkout and profile. Independent clones and worktrees retain private view metadata; explicitly authorized views may share physical immutable data as described in [shared-worktree-indexes.md](shared-worktree-indexes.md). Repository identity is an explicit UUID binding; it is not inferred from a URL, branch or commit. A local root locates a checkout and is never a content identity or remote authorization.

Each query resolves the active metadata once, acquires a lease on that named generation, and uses that generation for schema, vectors, graph and freshness inspection until completion. Publication stages a new generation and atomically switches metadata. Cleanup honors reader leases and retains generation tombstones. Unknown owners and abandoned coordination guards fail closed; recovery that cannot prove exclusion must remain an explicit administrative operation. Automatic portable recovery is not required to justify deleting an uncertain owner's lock.

Responses preserve distinct `indexGenerationId`, `sourceSnapshotId`, `repositoryId`, root and profile through the shared projection used by CLI, MCP and daemon. The legacy `snapshotId` field remains a generation alias for compatibility. Consumers must not use it as a content digest. A missing content identity stays unknown.

A recorded recipe hash identifies the canonical parameters available in index metadata, including explicit unknowns. `indexSpecHashScope=recorded-recipe-v1` limits that claim. The observation's missing fields describe reproduction limits: equal recipe hashes alone do not authorize vector reuse or establish the revision behind a mutable provider alias. Cache reuse additionally requires its explicit revision/account scope and effective adapter input. No complete provider-reproducibility claim is fabricated from configuration.

The source manifest covers only indexed files and hashes original bytes. Immutable source objects must be published before their manifest is activated, preserving BOM and newline bytes. Historical reads verify the retained object hash; live reads validate current source and report divergence. Retaining a table alone does not retain source history, and matching content does not prove semantic completeness.

The minimal cross-executor path transfers a single explicitly selected immutable source bundle over authenticated loopback endpoints reached through an authorized encrypted tunnel. The receiver selects the expected repository and content snapshot, validates every object and writes only to a private artifact directory. Portable references resolve only against that verified bundle. This provides historical source handoff without importing mutable database state. Importing vectors, running a distributed quota service or a base/overlay index requires separate measured justification and a stronger compatibility contract; they are not prerequisites for this source protocol.

Document caching remains opt-in and checkout/profile scoped. Local quota coordination budgets estimates among cooperating processes on a local filesystem; it does not claim a hard billing limit or cross-host coordination. The synthetic benchmarks do not establish a real-provider latency benefit and do not justify adopting an overlay.

Validation must distinguish process-isolated executors on one host from two physical machines. Current local tests and packed-artifact checks establish the former. The documented tunnel recipe still needs an authorized two-machine execution before claiming physical cross-machine validation.

## Required direction: independent views with shared physical data

The user clarified that efficient concurrent worktree/branch views across machines are a primary requirement. Per-checkout full collections are therefore a correctness baseline, not the desired storage architecture. A central index for one checkout cannot represent the private dirty states of other checkouts.

The target separates logical views from physical objects. Each checkout/profile owns an independently published immutable view manifest, identifying its files, chunk memberships, removals and current generation. Explicitly authorized checkouts in the same repository storage scope may reference common immutable source, parse and embedding objects. Repository identity authorizes the sharing scope; exact content and effective processing recipe determine reuse. Paths and symbols remain view-specific, and identical text does not make two file locations interchangeable.

On each executor, immutable searchable base segments can be shared by multiple views, with small replacement/addition overlays and tombstones per view. A modified file masks all superseded base chunks and graph edges for that file. Renames update membership and provenance even when vectors can be reused. Queries apply the selected view's masks before final ranking and limits, merge candidates across segments coherently, and expand retrieval when hidden candidates would otherwise underfill results. An embedding-object cache alone does not remove duplicate ANN storage; shared searchable segments are a separate implementation requirement.

A host service can share bounded caches and open segment handles among local clients. Clients retain independent operation contexts and pinned generations. Cache limits must include native/vector index memory as well as JavaScript allocations; adding a daemon alone does not prove reduced RSS. Compaction bounds overlay depth and segment count. Reachability from active views, pinned readers and explicitly retained snapshots governs collection; unreferenced objects and cached replicas need configured space/age budgets. Generation references and publication pins now drive local object collection; shared-object admission and replica retention apply separate budgets. See the implemented [retention contract](shared-source-retention.md).

Across machines, each executor can keep the segments needed for its active views and fetch missing immutable objects by verified identity from an authorized peer. Replication is selective, with eviction of unpinned cached segments; there is no need to synchronize full mutable database directories or keep permanent connectivity. Independent offline machines necessarily retain some duplicate local bytes. The goal is reuse within each machine and bounded, incremental replication across machines, rather than zero physical copies everywhere.

The existing per-checkout caches, collection staging copies and source retention must be migrated deliberately to this sharing scope. Validate with real Git worktrees, dirty/untracked changes, deletions and renames, multiple concurrent views, cold/warm access, compaction and reader retention. Measure embedding work, parse work, copied bytes, disk footprint, RSS and search correctness before claiming efficiency. The earlier synthetic microbenchmarks do not evaluate this architecture.

### Built CLI concurrency smoke

After building, run `node scripts/smoke-shared-worktrees.mjs`. It creates two actual Git worktrees in temporary directories, isolates all four XDG directories before importing built core code, and starts a deterministic OpenAI-compatible fixture on loopback. Two built CLI index processes start concurrently. The smoke requires one cold embedding request, independent view manifests, shared source inodes and a clone without copied base fragments. It then removes the source checkout, releases that view while its base is pinned, verifies the surviving view, releases it and runs repository GC. No external provider or production host is involved. The test uses two processes on one physical machine and cleans up its fixture server and temporary files.

## Implemented backend choice

[Shared worktree indexes](shared-worktree-indexes.md) implements this direction using native LanceDB copy-on-write manifests and dependency-aware retention. This preserves a unified ranking/filter surface instead of building a second overlay query engine. Source replicas use manifest/object protocol v2 with bounded retention. The benchmark justifies the measured local COW path; it does not prove remote ANN compatibility or a hard process RSS bound.
